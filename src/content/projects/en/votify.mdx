## The problem

An event full of projects has to decide who wins, and it is rarely one kind of person voting. The public votes for a favourite, the jury scores by criteria with different weights, and the organisers need to open, pause and close each voting without losing control.

## The solution

Votify organises everything around the event. Each event holds votings, and each voting has its projects, its teams and its type: standard, by criteria for the jury, or by criteria open to the public. The organiser manages roles, opens and pauses votings and reads the ranking, which shows the podium and the breakdown by criterion with its weight.

## Technical decisions

The code is split into layers: domain, application, infrastructure, API and the Blazor client. Each layer only knows the one inside it.

The design patterns solve concrete problems. Strategy: each voting type computes its results in its own class, so adding a type touches none of the others. State: an active, paused or finished voting accepts different actions. Observer: when a voting changes, notifications, scoring and analytics react without the voting service knowing them. Facade: controllers talk to one entry point per domain.

The AI summary of comments has a fallback: if the provider fails, the site keeps working with a summary computed without AI.
